# Conversational SOC Agent — Reference

> Design + implementation reference for the SAP Security conversational
> agent (`src/agent/`, `src/dashboard/pages/5_Agent.py`).
> Last updated 2026-04-30. Supersedes the prior `docs/agent_plan.md`
> (v1) and `docs/agent_plan_v2_insights.md` (v2 insights). The historical
> v1 doc was deleted when v1 was retired; see git history if needed.

## What it is

The agent lets an analyst compose ad-hoc security analysis from a
semantic model + a curated tool surface — in the spirit of Snowflake
Cortex Analyst / Snowflake Intelligence — but without arbitrary Python
execution and without giving up safety rails. The model has read-only
access to live HANA (SECURITY_LOGS, ANOMALIES, MODEL_VERSIONS) and the
SAP SOC API, plus an analyst-approved alert path.

The five architectural pillars (§1–§5) are non-negotiable; the rest of
the design is shaped around them.

---

## §1 — DB-side aggregation, smart row caps, no count wrapper by default

**Problem.** v1 capped `run_custom_query` at `LIMIT 1000`. Returning hundreds
of rows for the LLM to count in-context burns tokens, latency, and the
context window. The agent must be steered toward `GROUP BY`/`COUNT`/
`AVG`/regex extraction *server-side*, and the tool must structurally
prevent the lazy "fetch and count" path.

**Spec.**
- `run_custom_query` returns at most **20 rows** of raw data, regardless
  of any `LIMIT` the agent wrote. We enforce by appending/replacing with
  `LIMIT 21` (one more than the cap) and slicing.
- Response shape:
  ```json
  {
    "rows": [...up to 20 dicts...],
    "row_count_returned": 20,
    "truncated": true,
    "columns": ["source_ip", "anomaly_count", ...],
    "query_executed": "SELECT ... LIMIT 21",
    "elapsed_ms": 142
  }
  ```
- `truncated=True` when 21 rows came back. The agent is instructed (via
  system prompt) that **truncated does not mean "rerun with a higher
  limit"** — it means "rewrite as an aggregation".
- **Optional** `count_total: bool = False` parameter. When the agent
  *explicitly* needs a total, it sets `count_total=True` and we wrap
  the inner query in `SELECT COUNT(*) FROM (...)`. Default false because
  on HANA the wrapper re-scans without indexes and doubles latency on
  large filters; opt-in keeps the cost where the agent asked for it.

**Pushback on the original v1+ spec:** an *unconditional* COUNT wrapper
was the wrong default. The standard preview-engine trick (`LIMIT n+1` +
`truncated` flag) costs nothing extra and gives the agent the same
decision signal. Forcing COUNT on every dynamic query would have made
every analytical turn ~2× slower on a 5M-row table.

**System-prompt directives (excerpt — full text in §6):**
> When you need a count, do NOT fetch rows and count them. Write
> `SELECT COUNT(*) FROM ... WHERE ...`. When you need top-N, write
> `SELECT col, COUNT(*) AS n FROM ... GROUP BY col ORDER BY n DESC`.
> When you need to extract a value from a JSON column, use HANA's
> `JSON_VALUE(col, '$.path')`. When you need a substring match, use
> `LIKE` or HANA's regex functions. **Never** request raw rows in order
> to compute aggregates client-side.

## §2 — Error recovery loop with circuit breaker

**Problem.** Dynamic SQL means the agent will write broken SQL. Without
a brake, a 10-iteration loop devolves into a hallucination spiral
re-attempting the same `JOIN` that doesn't exist.

**Spec.**
- `run_custom_query` catches `hdbcli.dbapi.Error` (and the in-memory
  mock equivalent) and returns:
  ```json
  {
    "error": "<sanitized message, max 400 chars>",
    "error_code": "<vendor code if present>",
    "hint": "<optional one-liner: 'unknown column', 'syntax near \"GROPU\"', etc.>",
    "query_attempted": "<echo of the SQL we tried>"
  }
  ```
  Sanitization: strip stack traces, strip connection strings, cap at 400
  chars. The `hint` is generated by a small classifier (regex on the
  HANA error code: `259` = invalid column, `257` = syntax error, etc.).
- **Circuit breaker.** The agent loop tracks `sql_failures_this_turn`.
  Limit = **2 retries** (i.e. 3 total attempts at dynamic SQL per user
  turn). On the 3rd consecutive `run_custom_query` error, the
  orchestrator:
  1. Stops dispatching further `run_custom_query` calls in this turn.
  2. Injects a synthetic tool result:
     `{"error": "circuit_breaker_tripped", "message": "3 SQL failures
     in this turn; please rephrase or ask the user for clarification"}`.
  3. Forces a final assistant message — the agent must respond in
     natural language explaining what it tried and asking the user
     for help.
- The counter is **per user turn**, not per session. Each new user
  message resets it.
- Counter is on `run_custom_query` only — canned tools and helpers
  (`breakdown_by`, etc.) don't count, because they can't fail from
  agent-authored SQL.

**System-prompt directive (excerpt):**
> If a SQL query returns an error, read the `error` and `hint` fields,
> consult the schema (which is already in this prompt — see §3), and
> rewrite the query. You have at most **2 retries** before the system
> stops you. If you are unsure, call `describe_schema(table_name)` to
> get column-level metadata before retrying.

## §3 — Hybrid semantic model injection

**Problem.** Loading the full YAML semantic model into every prompt
wastes tokens; making the agent call a tool to see table names taxes
every analytical turn with a round-trip.

**Spec — split by access frequency.**

### In the system prompt (always loaded, prompt-cached)
Bare DDL only — table names, column names, types, NULLability:

```sql
-- SECURITY_LOGS  (~ N rows; primary fact table for ingested SAP logs)
DATETIME            TIMESTAMP       NOT NULL
SOURCE_IP           NVARCHAR(50)    NOT NULL
PORT_SERVICE        NVARCHAR(50)
EVENT_DESCRIPTION   NVARCHAR(500)
STATUS              NVARCHAR(50)
LOG_TYPE            NVARCHAR(50)
REQUEST_PATH        NVARCHAR(500)
SAP_APPLICATION     NVARCHAR(100)
REGION_CODE         NVARCHAR(20)
MACRO_REGION        NVARCHAR(50)
HTTP_METHOD         NVARCHAR(10)
SAP_SOURCE_TYPE     NVARCHAR(50)
SAP_APP_ENV         NVARCHAR(50)
LLM_TOTAL_TOKENS    INT             -- NULL for non-LLM traffic by design
LLM_COST_USD        DECIMAL(10,4)   -- NULL for non-LLM traffic by design
LLM_FINISH_REASON   NVARCHAR(50)
LLM_STATUS          NVARCHAR(50)
LLM_RESPONSE_TIME_MS INT
LLM_PROMPT_CATEGORY NVARCHAR(100)
LLM_ERROR_MESSAGE   NVARCHAR(500)
LLM_MODEL_ID        NVARCHAR(100)
LLM_PROMPT_TOKENS   INT

-- ANOMALIES  (anomaly events emitted by the detector)
ID                  NVARCHAR(64)    NOT NULL
SOURCE_IP           NVARCHAR(50)
SCORE               DECIMAL(10,6)   -- isolation-forest score; lower = more anomalous
THREAT_LEVEL        NVARCHAR(20)    -- HIGH | MEDIUM | LOW
DETECTED_AT         TIMESTAMP
DETECTOR            NVARCHAR(50)    -- 'isolation_forest' | 'llm' | ...
PIPELINE_MTTD_MS    BIGINT
E2E_MTTD_MS         BIGINT
EVIDENCE_JSON       NCLOB           -- JSON; use JSON_VALUE() to extract
CREATED_AT          TIMESTAMP

-- MODEL_VERSIONS  (model registry)

MODEL_TYPE          NVARCHAR(50)
HYPERPARAMS_JSON    NCLOB
FEATURES_JSON       NCLOB
CV_SCORES_JSON      NCLOB
```

This block costs ~700 tokens, sits inside the cached system prompt
(so it's effectively free after the first call in a session), and
gives the LLM enough to compose ~80% of useful queries on its own.

### Behind a tool (loaded on demand)
`describe_schema(table_name: str)` returns the rich metadata for one
table only:

```python
{
  "table": "ANOMALIES",
  "row_count_estimate": 12450,
  "columns": [
    {
      "name": "SCORE",
      "type": "DECIMAL(10,6)",
      "meaning": "Isolation-forest anomaly score. Lower = more anomalous. Threshold for HIGH is ~ -0.3, MEDIUM ~ -0.1.",
      "null_semantics": "Always populated for isolation_forest detector; may be NULL for llm detector pre-2026-04-21.",
      "common_filters": ["SCORE < -0.3", "SCORE BETWEEN -0.3 AND -0.1"]
    },
    ...
  ],
  "metrics": {
    "anomaly_rate_per_min": "COUNT(*) / (window_minutes * 1.0)",
    "mttd_p95_ms": "PERCENTILE_CONT(0.95) WITHIN GROUP (ORDER BY PIPELINE_MTTD_MS)",
    "high_severity_share": "SUM(CASE WHEN THREAT_LEVEL='HIGH' THEN 1 ELSE 0 END) / COUNT(*)"
  },
  "example_queries": [
    "SELECT SOURCE_IP, COUNT(*) FROM ANOMALIES WHERE DETECTED_AT > ADD_HOURS(NOW(), -24) GROUP BY SOURCE_IP ORDER BY 2 DESC",
    "SELECT JSON_VALUE(EVIDENCE_JSON, '$.failed_logins') AS fl FROM ANOMALIES WHERE THREAT_LEVEL='HIGH' AND fl IS NOT NULL"
  ]
}
```

Stored as `src/agent/semantic_model.yaml`, loaded once at module import,
served by `describe_schema`. The bare DDL in the system prompt is
**generated from the same YAML** at startup — single source of truth.

## §4 — Observation masking + smart truncation

**Problem.** A 10-iteration loop with raw tool outputs (especially live
SAP log payloads, which can be multi-KB JSON) blows the context window
and degrades reasoning ("context rot").

**Spec — two-layer defense.**

### Layer A: Smart truncation at the tool boundary (primary)
Every tool wraps its return value through `_truncate_for_llm(payload)`:
- Lists: cap at 20 items; append `"...(N more truncated)"` placeholder.
- Strings > 1500 chars: head/tail cut → first 500 chars + `"...[TRUNCATED N chars]..."` + last 500 chars.
- JSON/dict values: recursive — same rules per leaf.
- Raw log payloads (anything from `get_current_logs_sample` or
  `EVIDENCE_JSON` extracts): always truncated to head/tail.

This applies *before* the observation ever enters the agent's message
history. It's the most important of the two layers.

### Layer B: Observation summarization for old turns (secondary)
Once an observation is older than **3 agent iterations** *and* its
serialized size exceeds **1KB**, the orchestrator replaces the
`tool_result` content with a synopsis:

```
[Turn 2 — run_custom_query: returned 14 rows, columns=[source_ip,
anomaly_count, max_score]. Top row: source_ip=10.0.0.1,
anomaly_count=312, max_score=-0.81. Full output omitted to save context.]
```

The synopsis is generated deterministically from the structured tool
return (no extra LLM call): for tabular results, take row count + column
list + first row; for scalars, keep them verbatim; for errors, keep the
error message verbatim (errors are small and load-bearing for the
circuit breaker).

**Why not blunt masking on everything > 3 turns:** legitimate
follow-ups like *"of those IPs from earlier, which also hit the LLM
endpoints?"* depend on prior content being referenceable. Small
observations (< 1KB) stay verbatim forever — Anthropic prompt caching
makes that essentially free across iterations. We only summarize when
the observation is genuinely heavy.

**Pushback on a size-blind 3-turn mask:** the original constraint as
stated would erase load-bearing context. The size-gated version
preserves the budget protection while keeping small structured results
addressable.

## §5 — Agent tracing and observability in the UI

**Problem.** A 10-iteration loop = an analyst staring at a spinner for
20+ seconds with no idea what's happening, and no audit trail of what
the agent did.

**Spec.**
- Use `st.status(label, expanded=False)` per tool call — *not*
  `st.toast`. Toasts disappear; the analyst loses the audit trail and
  cannot scroll back to verify which tool produced which result.
  `st.status` containers persist in the chat message and are the
  evidence record.
- The agent orchestrator is an **async generator** that yields
  `AgentEvent` records:
  ```python
  AgentEvent.tool_started(tool_name, args)       # → opens an st.status
  AgentEvent.tool_finished(tool_name, summary)   # → closes it (state="complete")
  AgentEvent.tool_failed(tool_name, error, retry_n)  # → state="error"
  AgentEvent.text_delta(chunk)                   # → streamed into st.write_stream
  AgentEvent.final(message)                      # → terminal event
  ```
- Streamlit page consumes the generator inside the assistant
  `st.chat_message`:
  ```python
  with st.chat_message("assistant"):
      for ev in agent.run(user_msg):
          if ev.kind == "tool_started":
              status = st.status(f"🔍 {ev.human_label}", expanded=False)
              status.write({"args": ev.args})
          elif ev.kind == "tool_finished":
              status.update(label=f"✓ {ev.human_label}", state="complete")
              status.write(ev.summary)
          elif ev.kind == "tool_failed":
              status.update(label=f"⚠ {ev.human_label} (retry {ev.retry_n})", state="error")
          elif ev.kind == "text_delta":
              text_placeholder.markdown(text_so_far + ev.chunk)
          ...
  ```
- Human labels are tool-specific:
  - `get_top_suspicious_ips` → "Querying anomaly counts by source IP…"
  - `breakdown_by` → "Breaking down {metric} by {dimension}…"
  - `run_custom_query` → "Running custom SQL…"
  - `submit_alert` → "Drafting alert preview…"
  - `post_alert_message` → "Sending alert to SAP…"
- Reserve `st.toast` for terminal, fire-and-forget events:
  alert successfully sent (`✓ Alert delivered`), circuit breaker
  tripped (`⚠ SQL failed 3× — agent stopped`).
- Final assistant text streams via `st.write_stream` against the
  `text_delta` events.

| **16** | **`correlate(dim_a, dim_b, hours, top_n=20)`** | **v2** | co-occurrence matrix |

### Allowed values (validated server-side; reject anything else)
- `metric ∈ {anomaly_count, log_volume, mttd_p50, mttd_p95, high_severity_count, login_failure_count, llm_token_total, llm_cost_total}`
- `dimension ∈ {source_ip, sap_application, region_code, macro_region, log_type, http_method, threat_level, llm_prompt_category, sap_source_type}`
- `hours ∈ [1, 720]` (30 days max)
- `bucket_minutes ∈ {1, 5, 15, 30, 60, 240, 1440}`
- `top_n ∈ [1, 50]`

Each helper is a SQL template parameterized only by these whitelisted
values. No string interpolation of agent-supplied values into SQL beyond
the whitelist — eliminates the SQL-injection surface that exists in
`run_custom_query`.

### Helper SQL templates (sketches)

**`breakdown_by(metric="anomaly_count", dimension="source_ip", hours=24)`**:
```sql
SELECT {dimension} AS dim, COUNT(*) AS metric_value
FROM ANOMALIES
WHERE DETECTED_AT > ADD_HOURS(CURRENT_TIMESTAMP, -:hours)
GROUP BY {dimension}
ORDER BY metric_value DESC
LIMIT 50
```
Returns `[{dim, metric_value}]`. Column choice and table choice depend
on `metric` (e.g. `metric=log_volume` → `FROM SECURITY_LOGS`).

**`compare_windows(metric="anomaly_count", window_a_h=1, window_b_h=24)`**:
```sql
SELECT
  SUM(CASE WHEN DETECTED_AT > ADD_HOURS(CURRENT_TIMESTAMP, -:a) THEN 1 ELSE 0 END) AS window_a,
  SUM(CASE WHEN DETECTED_AT > ADD_HOURS(CURRENT_TIMESTAMP, -:b)
       AND DETECTED_AT <= ADD_HOURS(CURRENT_TIMESTAMP, -:a) THEN 1 ELSE 0 END) AS window_b
FROM ANOMALIES
WHERE DETECTED_AT > ADD_HOURS(CURRENT_TIMESTAMP, -:b)
```
Returns `{window_a, window_b, delta_abs, delta_pct}`.

**`time_series(metric="anomaly_count", hours=24, bucket_minutes=60)`**:
```sql
SELECT
  SERIES_ROUND(DETECTED_AT, 'INTERVAL :bucket_minutes MINUTE') AS bucket,
  COUNT(*) AS metric_value
FROM ANOMALIES
WHERE DETECTED_AT > ADD_HOURS(CURRENT_TIMESTAMP, -:hours)
GROUP BY 1 ORDER BY 1
```
Returns `[{bucket, metric_value}]`. Streamlit page renders as
`st.line_chart` automatically when this tool result lands.

**`correlate(dim_a="source_ip", dim_b="event_description", hours=24, top_n=20)`**:
```sql
SELECT {dim_a} AS a, {dim_b} AS b, COUNT(*) AS n
FROM SECURITY_LOGS
WHERE DATETIME > ADD_HOURS(CURRENT_TIMESTAMP, -:hours)
GROUP BY {dim_a}, {dim_b}
ORDER BY n DESC
LIMIT :top_n
```
Returns `[{a, b, n}]` — co-occurrence ranked.

## §7 — System prompt outline

```
You are the SAP SOC security analyst assistant. You have read-only
access to live SAP HANA data and the SAP SOC API.

# Style
- Be concise. Lead with the answer; show numbers; flag threats clearly.
- Before issuing any tool call beyond a trivial counter, briefly state
  your hypothesis ("I expect we'll see X concentrated in Y because…").
  After results land, comment on whether they matched.

# Schema (always available — do not call describe_schema just to learn
# table or column names, only call it for rich metadata)
[ ...DDL block from §3... ]

# Tool selection rules
- For canned questions (counts, top-N, MTTD), prefer the named tools
  (#1–#6, #8–#10).
- For "compare/breakdown/trend/correlate" questions, use the v2
  helpers (#13–#16).
- Use run_custom_query ONLY when no helper fits. When you do:
    * NEVER fetch raw rows to count them. Use SELECT COUNT(*).
    * NEVER fetch raw rows to aggregate them. Use GROUP BY.
    * For JSON columns (EVIDENCE_JSON, *_JSON), use JSON_VALUE(col, '$.path').
    * Results are capped at 20 rows. truncated=True means rewrite as
      an aggregation, not "rerun with bigger limit".
    * On error, read error+hint, optionally call describe_schema, and
      rewrite. You have 2 retries before the system stops you.

# Iteration budget
- You have at most 10 tool-use rounds per user message. Prefer fewer.

# Alerting
- submit_alert returns a preview only. The user must click "Approve &
  send" in the UI before anything is delivered. Never claim an alert
  has been sent until you have observed a post_alert_message tool
  result with ok=true.

# Honesty
- If HANA returns {"error": "HANA unavailable"} or any tool errors out
  beyond your retry budget, say so plainly. Do not invent numbers.
```

## §8 — Agent loop pseudocode (with §2 + §4 enforcement)

```python
async def run(self, user_msg: str) -> AsyncIterator[AgentEvent]:
    self.messages.append({"role": "user", "content": user_msg})
    sql_failures = 0
    iterations = 0

    while iterations < settings.agent_max_iterations:  # 10
        # Apply Layer B observation summarization to messages older than 3 turns
        msgs_for_api = self._compact_old_observations(self.messages, age_threshold=3)

        response = await self.client.messages.create(
            model=settings.agent_model,
            system=self.system_prompt,           # cached
            tools=TOOL_SCHEMAS,
            messages=msgs_for_api,
            max_tokens=2048,
        )

        for block in response.content:
            if block.type == "text":
                yield AgentEvent.text_delta(block.text)
            elif block.type == "tool_use":
                yield AgentEvent.tool_started(block.name, block.input)
                try:
                    result = await dispatch_tool(block.name, block.input)
                except Exception as e:
                    result = {"error": str(e)[:400]}

                # Smart truncation (Layer A) before storing
                result = _truncate_for_llm(result)

                # Circuit breaker accounting
                if block.name == "run_custom_query" and "error" in result:
                    sql_failures += 1
                    yield AgentEvent.tool_failed(block.name, result["error"], sql_failures)
                    if sql_failures >= 3:
                        result = {"error": "circuit_breaker_tripped",
                                  "message": "3 SQL failures this turn — stopping."}
                        # No more run_custom_query dispatches this turn;
                        # we still let the loop run so the agent can write
                        # a final natural-language answer.
                else:
                    yield AgentEvent.tool_finished(block.name, _summary(result))

                self._append_tool_result(block.id, result)

        if response.stop_reason == "end_turn":
            yield AgentEvent.final(self.messages[-1])
            return
        iterations += 1

    yield AgentEvent.final({"text": "Iteration budget exhausted."})
```

`_compact_old_observations` walks `messages`, finds `tool_result`
blocks at index < `len(messages) - age_threshold * 2`, and replaces
content with the synopsis when serialized size > 1KB.

## §10 — Verification (additions over v1's verification)

1. **Truncation unit tests:** dict with 5KB string → head/tail cut to ~1KB; list of 100 dicts → 20 + placeholder; nested 3-deep JSON → leaves truncated independently.
2. **Circuit-breaker integration test:** seed agent with a prompt that intentionally writes 3 broken queries; assert exactly 3 `run_custom_query` calls, then a final assistant message containing the words "stopped" or "unable".
3. **Helper whitelist tests:** `breakdown_by(dimension="DROP TABLE")` → `ValueError` before any SQL runs.
4. **Schema-prompt size test:** rendered DDL block ≤ 1000 tokens (tiktoken count).
5. **End-to-end manual scenarios** (in addition to v1's five):
   - "Has the brute-force rate on `sap-api-bi` changed in the last 6 hours vs the prior 18?" → expect `compare_windows` call.
   - "Which regions have the worst MTTD today?" → expect `breakdown_by("mttd_p95", "region_code", 24)`.
   - "Are SQL-injection events coming from the same IPs as failed logins?" → expect `correlate` or two custom queries with reasoning.
   - "What's weird in the current 30-min window?" → expect `get_current_window_info` + `breakdown_by` + hypothesis-driven follow-up.
   - **Failure-mode scenario:** "Find me the rows in TABLE_THAT_DOESNT_EXIST" → expect 3 retries then a graceful "I can't find that table" response.

## §10b — Cross-cutting implementation pins (decided 2026-04-29)

These are not new sections but were left fuzzy in v2 §1–§9. Pinning here
so they don't become open questions during coding.

- **Anthropic prompt caching.** Mark the system prompt (instructions +
  DDL block from §3) and the `tools=[...]` schema array with
  `cache_control={"type": "ephemeral"}` on every `messages.create`
  call. Both are stable across a session; caching them is real money.
- **Per-tool query timeout.** Wrap every HANA-backed tool body in
  `await asyncio.wait_for(..., timeout=10.0)`. Timeout returns
  `{"error": "query_timeout", "elapsed_ms": 10000}`. Counts toward the
  circuit breaker only for `run_custom_query` (canned tools and helpers
  timing out is infra failure, not hallucination).
- **`describe_schema` row-count source.** Use HANA's
  `M_TABLE_PERSISTENCE_STATISTICS` view, not `SELECT COUNT(*)`. In mock
  mode, return `len(memory_backend)`.
- **Async generator → Streamlit bridge.** Pattern: `agent.run()` is
  `AsyncIterator[AgentEvent]`; the page wraps it in a sync generator
  via a thread-pumped `queue.Queue` and feeds `st.write_stream()` for
  text deltas, while iterating tool events on the main thread for
  `st.status` updates. Skeleton:
  ```python
  def _events(coro):
      q: queue.Queue = queue.Queue()
      SENTINEL = object()
      def runner():
          async def pump():
              async for ev in coro: q.put(ev)
              q.put(SENTINEL)
          asyncio.run(pump())
      threading.Thread(target=runner, daemon=True).start()
      while (ev := q.get()) is not SENTINEL: yield ev
  ```
- **Tool input validation guard.** Every tool function starts with a
  pydantic model validation of its args. Helpers (`breakdown_by` etc.)
  validate `metric`/`dimension` against the §6 whitelists and raise
  `ToolValidationError` before any SQL touches HANA.
- **Render hints.** Each tool result includes a `_render` field hinting
  the page (`"line_chart" | "bar_chart" | "table" | "scalar" | "raw"`).
  v2 page uses this to pick `st.line_chart`/`st.dataframe`/etc. without
  inferring from tool name.

## §11 — Out of scope for v2 (deliberately deferred)

- **Sandboxed Python `exec`** for arbitrary pandas analysis. Hardening
  is real engineering work; the curated helpers + `run_custom_query`
  cover the same ground for our schema. Revisit only if helpers prove
  too rigid in real use.
- **Vector / RAG over ARCHITECTURE.md / MODEL_JOURNAL.md.** Corpus is
  small enough to inline if needed; not justifying infra now.
- **Auto-discovered metrics.** Semantic model is hand-maintained — the
  right call for one schema and a 2-week timeline.
- **Multi-step plan generation** (chain-of-thought planning before tool
  use). Anthropic's tool-use already does this implicitly; an explicit
  planner adds complexity without clear win at our scale.

## §12 — Pushbacks summary (for the audit trail)

Three modifications to the originally proposed constraints:

1. **§1, COUNT wrapper:** changed from "always wrap" to **opt-in via
   `count_total: bool`**. Reason: HANA re-scans on subquery COUNT;
   doubling per-turn latency is too expensive when `LIMIT n+1` +
   `truncated` flag conveys the same signal for free.
2. **§4, observation masking:** changed from "mask everything > 3
   turns" to **size-gated (>1KB) summarization with deterministic
   synopsis**. Reason: blunt masking breaks legitimate cross-turn
   references; small structured results stay free under prompt cache.
3. **§5, st.toast for progress:** changed to **`st.status` for tool
   calls, `st.toast` for terminal events only**. Reason: toasts
   disappear, destroying the audit trail an analyst needs to verify
   which tool produced which number.

The other two constraints (§2 circuit breaker, §3 hybrid schema
injection) are integrated as specified — they were correct as written.
